## Prompt A — Foundation: shadcn/ui + Tailwind token wiring

**Depends on:** doctrine files on disk.
**Blocks:** B, D, E.
**Estimated size:** medium (config + generated components + CSS token layer refactor).
**Approval required:** yes — this prompt runs `npx shadcn init` and adds Radix packages to `frontend/package.json`. Pause after the `npm install` step and ask Justin to confirm the package changes before proceeding to component generation.

### Read first, in order

1. `AGENTS.md` (repo root posture)
2. `Blueprints/specs/design/component-lock-v1.md` (component grammar)
3. `Blueprints/specs/design/team-theme-contract-v1.md` (§Terminology, §Token allow/deny — you need the token names)
4. `Blueprints/specs/omen-ux-ui-design-system-v1.md` §Color System (the base palette hexes)
5. `frontend/tailwind.config.js` and `frontend/src/index.css` (what already exists)

### Goal

Install shadcn/ui in `frontend/`, wire it to the existing Omen CSS custom property layer, and generate the primitive components named in `component-lock-v1.md`. Do not sweep any page code yet — that's prompt D.

### Scope

- `frontend/package.json` (adds Radix + a few utility packages)
- `frontend/tailwind.config.js` (theme extension mapping CSS variables to Tailwind tokens)
- `frontend/src/index.css` (no palette changes; only add shadcn-required variables like `--radius` if missing)
- `frontend/src/components/ui/` (new directory — canonical primitives live here)
- `frontend/src/lib/utils.js` (shadcn's `cn` helper — required)
- Optional: `frontend/components.json` (shadcn config file generated by init)

Out of scope: any page in `frontend/src/pages/`, any file in `frontend/src/components/` outside `ui/`, any change to team-theming CSS, any change to `--color-*` values.

### Steps

1. **Read the doctrine listed above and summarize your understanding back to Justin** before touching the tree. Two sentences: what components you'll generate, what tokens they'll read. Wait for a "go."
2. Run `npx shadcn@latest init` in `frontend/`. Choose CSS variables (not the default `tailwind.config` inline colors). Use `--color-*` naming so shadcn's variables map onto Omen's existing tokens.
3. **STOP — approval gate.** Show Justin the `package.json` diff and the newly-generated files. Wait for confirmation before continuing.
4. Generate primitives one at a time with `npx shadcn add`:
   - `button` → wire the five variants named in `component-lock-v1.md` §1 (primary, secondary, tertiary, danger, link) and three sizes (sm/md/lg). Add a `tone` prop for `accent` (default) / `omen`.
   - `input`, `textarea` → §2 API.
   - `tabs` → will host both `SegmentedControl` (§3) and `TabNav` (§3.1) via list-style prop.
   - `radio-group` → will host `RadioCardGroup` (§3.1) via a card-style rendering wrapper.
   - `card` → §4 API. Add `variant` prop (solid / outlined / empty / error / preview) and `tone` prop (neutral / omen / risk).
   - `alert` → §4.1.
   - `badge` → will host `Chip` (§H1 taxonomy note in doctrine audit — treat Chip as a Badge subclass with `variant="chant"` and `variant="preview"` sub-variants).
   - `label` → for form field labels.
5. Build the type-scale primitive `<Text as="h1|h2|…" role="display|h1|h2|h3|body|body-sm|label|eyebrow|chip">` in `frontend/src/components/ui/text.jsx`. Read `component-lock-v1.md` §5 for the exact type role definitions. Do not use shadcn for this — it's Omen-specific.
6. Build the layout primitives (not in shadcn): `PageHero`, `MarketingHero`, `PlatformBadge`, `TeamBadge`. Read `component-lock-v1.md` §5 for `PageHero`; use the doctrine audit's H1 for `TeamBadge` and `PlatformBadge` (rendered per team / per platform brand tokens, no team-theme override).
7. Wire Tailwind's `theme.extend.colors` to read `--color-*` variables so `bg-accent`, `text-omen`, `border-risk-high`, etc. work.
8. Add a `frontend/src/components/ui/index.js` barrel export.
9. **Do not** touch `frontend/src/App.jsx`, any page, or any existing component. Only `ui/` gets touched in this prompt.

### Verification

- `npm run build` succeeds without warnings from unknown Tailwind classes.
- `npm run dev` starts and the app looks visually **identical** to `main` (no page uses the new components yet — this prompt is scaffolding only).
- Every primitive exported from `frontend/src/components/ui/index.js` is importable in isolation (`import { Button } from '@/components/ui'`).
- Zero regressions in existing pages.

### Definition of done

- All primitives named in `component-lock-v1.md` §1–5 and the sibling components in §3.1, §4.1 exist under `frontend/src/components/ui/`.
- Tailwind config reads from CSS variables; no hardcoded palette hexes in components.
- `package.json` diff shows only expected new dependencies (Radix primitives + `class-variance-authority` + `clsx` + `tailwind-merge`).
- One commit per major step, or one clean commit at end — Justin's call.

## Prompt B — Team token contract + room-mode + three switches

**Depends on:** Prompt A landed.
**Blocks:** C, D (partially), E.
**Estimated size:** medium-large (CSS variable refactor + per-team data field + JS resolver scaffolding).
**Approval required:** no (all changes are in-repo code, CSS, data).

### Read first, in order

1. `Blueprints/specs/design/team-theme-contract-v1.md` — full doc.
2. `Blueprints/audits/2026-07-10-team-theme-contract-verification.md` — the α values and the fallback cascade you'll implement.
3. `slops-saloon/Blueprints/specs/team-colorway-system-spec-v1.md` §2.1, §2.3, §7 — L1 authored per-team values for Eagles, Cowboys, Chiefs.
4. Current `frontend/src/index.css` — you'll refactor the team-theming block.
5. Current `frontend/src/data/nflTeams.js` (or wherever the 32-team data currently lives) — you'll add fields.

### Goal

Implement the token contract in CSS + data + JS such that:
- Team color reaches the shell at the room-mode's α, not at 100%.
- Text, role, position, platform tokens stay untouched by team selection.
- The three switches (Accent source / Surface mode / Team) resolve at page load and paint the correct state.
- Each team has an `authoredSurfaceDefault` field for the "Auto" surface mode.

Do NOT change any page's markup or add the `data-room` attribute yet — that's part of D. This prompt lands the tokens and resolution logic; D wires up the `data-room` attribute per page.

### Scope

- `frontend/src/index.css` — refactor team-theme override block per the contract's allow/deny lists.
- `frontend/src/data/nflTeams.js` (or equivalent) — add `authoredSurfaceDefault: 'dark' | 'light'` per team.
- `frontend/src/lib/teamTheme.js` (new or extend existing) — token population.
- `frontend/src/lib/themeResolver.js` (new) — applies switches A + B + C to the document root, returns the resolved token state.
- `frontend/src/providers/ThemeProvider.jsx` (new or extend) — reads user prefs, calls resolver, applies `data-*` attributes on `<html>`.

Out of scope: the contrast+collision check (that's prompt C — but leave hooks in the resolver so C can plug in).

### Steps

1. **Read the doctrine + verification memo. Summarize back to Justin** what you'll do in three sentences. Wait for a "go."
2. In `index.css`, split the current team-theming block into three attribute-selector layers:
   - `[data-surface="dark"]` — Omen dark shell tokens (`--color-bg`, `--color-surface-*`, `--color-border`, `--color-text-*`).
   - `[data-surface="light"]` — Omen light shell tokens.
   - `[data-accent-source="team"][data-team="WAS"] { ... }` — per-team token block. Populates `--color-team-primary`, `--color-team-secondary`, `--color-team-accent`, `--color-team-surface` (as `color-mix(in oklab, var(--color-team-primary) var(--room-alpha), var(--color-bg))`), `--color-team-surface-card` (see below).
3. Add a `[data-room]` attribute layer that sets `--room-alpha`:
   - `[data-room="owner"] { --room-alpha: 5%; }`
   - `[data-room="gm"] { --room-alpha: 14%; }`
   - `[data-room="locker"] { --room-alpha: 35%; }` (mid-range default; per-team overrides come later)
4. Add the fallback for `--color-team-surface-card`. Two paths:
   - Default: `#1C1C1E` (neutral charcoal — Omen `--color-surface-1`).
   - Override for teams that fail all three of Rule 3a/3b/3c at neutral charcoal (verified list from `2026-07-10-team-theme-contract-verification.md`: Packers, Steelers, Eagles): use a lifted card fill (e.g., `#2A2A2C` or a subtle team-tinted card). Encode which teams get the lift in `nflTeams.js` as a `cardLift: true` field.
5. Populate `--color-accent` under `[data-accent-source="team"]`. Compute via the cascade in JS (see `themeResolver.js`) and set it as a CSS variable on `document.documentElement`. Don't try to do the cascade purely in CSS — it needs contrast math.
6. In `frontend/src/data/nflTeams.js`, add per team: `primary`, `secondary`, `accent`, `authoredSurfaceDefault` (`dark` or `light`), `cardLift` (bool, defaults false), `chants` (array of chant strings — for future use, safe to add empty array now).
7. In `frontend/src/lib/themeResolver.js`, implement:
   - Read user prefs from wherever they currently live (Supabase user profile, localStorage — check existing code).
   - Resolve Switch A (accent source), Switch B (surface mode, respecting `auto` → team's `authoredSurfaceDefault`), Switch C (team).
   - Compute `--color-accent` via cascade (stub the contrast checks; prompt C will fill them in).
   - Apply `data-surface`, `data-accent-source`, `data-team` on `<html>`.
   - Return the resolved state for consumers.
8. Add contrast-check hooks in `themeResolver.js` — placeholder functions that always return `true` for now. Prompt C fills them in.
9. Wire `ThemeProvider` into `App.jsx` so it runs before pages mount.

### Verification

- On `main` (Omen mode, dark), the app renders identically to before this prompt. No visual change.
- Switching to Team mode on `/account/appearance` should still work (still uses the old MODE selector — that's E's job to fix). The visual outcome may differ from `main` because the token contract is now in effect; verify that:
  - Shell tokens carry team color at α (visible as a wash, not full-strength).
  - Text remains bone-white (or dark, per surface mode).
  - Position chips are unchanged (still color-coded per position).
  - Risk indicators unchanged (Deep Crimson stays Deep Crimson regardless of team).
- Run the Commanders test manually: pick Washington, browse `/football` — expect burgundy shell + charcoal card + gold accent (all visibly distinct). Not the full-burgundy drowning that shipped previously.
- Run the Dolphins test: pick Miami, browse `/football` — expect aqua-tinted shell + charcoal card + white accent (aqua cascade doesn't clear at 35% α — verified).

### Definition of done

- CSS variable layer refactored per the contract's allow/deny lists.
- 32 teams have full data blocks including `authoredSurfaceDefault`.
- Theme resolver runs at page load and applies the correct `data-*` attributes.
- No page code changed yet; all changes are in tokens + data + resolver.
- Manual smoke test on Commanders + Dolphins matches expected outcome.

## Prompt C — Contrast + collision resolver + 32-team verification report

**Depends on:** Prompt B landed (needs `themeResolver.js` scaffolded).
**Blocks:** any code that relies on the cascade producing correct results.
**Estimated size:** small-medium.
**Approval required:** possibly — if you add `chroma-js` as a dep (~30KB). If you hand-roll the WCAG + ΔE math, no approval needed.

### Read first, in order

1. `Blueprints/specs/design/team-theme-contract-v1.md` §Contrast enforcement, §Fallback cascade.
2. `Blueprints/audits/2026-07-10-team-theme-contract-verification.md` — includes reference math + expected outcomes per team.
3. Current `frontend/src/lib/themeResolver.js` — you'll fill in the contrast-check hooks.

### Goal

Implement the four contrast rules and role-collision distance check from the contract. Wire them into the resolver so the accent cascade produces correct results. Then output a verification report showing which teams pass / fail / cascade to which accent, at each room mode.

### Scope

- `frontend/src/lib/contrastMath.js` (new) — small module with `wcagContrast`, `deltaE_CIELAB`, `mixLinear` (or use `color-mix(in oklab)` at runtime — depends on browser target).
- `frontend/src/lib/themeResolver.js` — fill in the hooks left by prompt B.
- `scripts/verify-team-themes.js` (new — Node script) — walks all 32 teams and prints the verification table.

Out of scope: adding a UI surface for the verification report (that's a nice-to-have for later).

### Steps

1. **Read the doctrine + verification memo. Summarize your plan.** Wait for "go."
2. In `contrastMath.js`, implement (or import via `chroma-js` — ask first if you want to add the dep):
   - `wcagContrast(fg, bg)` returning a ratio.
   - `deltaE_CIELAB(a, b)` returning a Lab-space distance.
   - `mixLinear(c1, c2, alpha)` — sRGB linear-space blend, an approximation of `color-mix(in oklab, ...)`. Close enough for pass/fail; annotate that oklab is the source-of-truth blend and browsers will do it exactly.
3. In `themeResolver.js`, implement four checks matching the contract's Rules 1–4:
   - Rule 1: text on shell ≥ 4.5:1.
   - Rule 2: accent on shell ≥ 3:1.
   - Rule 3: card differentiation via 3a (luminance ≥ 3:1) OR 3b (ΔE ≥ 15) OR 3c (border passes 3:1 vs both). Report which of a/b/c satisfies.
   - Rule 4: accent vs. `--color-omen` and `--color-risk-high` ≥ 20 ΔE.
4. Implement the accent cascade: primary → secondary → white → black → complementary color-wheel-derived → Omen brass. Log which step won.
5. Write `scripts/verify-team-themes.js` to walk all 32 teams and print a table:
   - Team name, room mode, α used.
   - Rule 1/2/3/4 pass/fail.
   - Which fallback step the accent came from.
   - Card lift flag if needed.
6. Run the script; capture the output in `Blueprints/audits/2026-07-10-team-themes-verification-report.md` (append a "Run 1" section with the results).
7. If any team fails Rule 1 (text illegibility) at any room mode, flag it — that's a design bug requiring an authored fix, not a fallback. Rules 2 and 4 are expected to fail for many teams (that's what the cascade is for).

### Verification

- Verification report generated for all 32 teams.
- Stress-test teams from the verification memo (Commanders / Dolphins / Packers / Chiefs / Steelers) produce the outcomes predicted in that memo.
- App still runs. The Commanders test now produces the same visual as after prompt B (this prompt improves correctness of the resolver, not visual output — assuming B's stubs happened to guess right).
- Any team where the resolver produces a different accent than the verification memo predicts is either (a) a math bug in your implementation, or (b) a math bug in the verification memo. Investigate and note in the report.

### Definition of done

- Cascade produces the expected accent for the 5 stress teams.
- Verification report exists and is committed.
- Any teams flagged as Rule 1 failures (text illegibility) are called out with recommended per-team card-lift or authored-α overrides.
