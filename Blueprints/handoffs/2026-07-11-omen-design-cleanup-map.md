## Authority Model

Proposed hierarchy, root to leaf:

1. **Root doctrine** — `CLAUDE.md` / `AGENTS.md` (routing + read-order only). **Needs a fix**: currently points to `Blueprints/specs/omen-ux-ui-design-system-v1.md` as the on-demand token/component reference; should point to `Blueprints/specs/design/component-lock-v1.md` and `team-theme-contract-v1.md` instead.
2. **Design specs (current)** — `Blueprints/specs/design/component-lock-v1.md` (component API/tokens) and `team-theme-contract-v1.md` (team-skin override rules). These are the live authority. Both are marked "pre-implementation" — authority precedes implementation here, which is fine as long as the gap is tracked (see REBUILD row on `themeMode.js`).
3. **Design spec (superseded)** — `Blueprints/specs/omen-ux-ui-design-system-v1.md`. Still may hold non-component doctrine `component-lock-v1.md` doesn't cover (verify before archiving fully); component/token portions are dead.
4. **Token source of truth** — `frontend/src/index.css`. Every color, spacing, and semantic token used across the app should trace to a custom property declared here. Any component or page defining its own raw color value is, by definition, out of compliance with this layer.
5. **Team-surface logic (should be, not yet fully)** — `frontend/src/lib/themeMode.js` (mode/apply orchestration) + `frontend/src/lib/teamTemplate.js` (palette source) + `frontend/src/lib/nflTeams.js` (raw team color data). Per the founder's ask, **these three files together should be the only place team-surface logic lives** — no component or page should read raw team colors or branch on team identity directly. Today this is *mostly* true (HelpButton/AppearancePicker/Header/Appearance/Account all consume via `var(--color-team-*)` rather than redefining), but `themeMode.js`'s shell-override behavior itself needs the contrast-guard rebuild from `team-theme-contract-v1.md` before this layer is actually compliant with layer 2.
6. **Audits/reviews** (`Blueprints/audits/`, `Direction/reviews/`) — evidence and diagnosis, not authority. They justify why a spec says what it says; they don't govern independently.
7. **Prompts** (`Blueprints/prompts/`) — execution instructions for a specific past or current task. Never authority; the repo's own README already treats them this way.
