### 2026-10-14 scope correction and first integration cut

The founder corrected an important conflation before implementation continued: **Find a Trade was
not part of the original Trade canvas.** The original canvas governs the league-aware `Type a trade`
and `Build a trade` experience. Find is the later sports-game-style idea: Omen scans the league and
returns a reviewable batch of possible deals. Its separate authority is `TradeFindReview-v1.md` and
the T2/T3 sections of `omen-trade-rework-v1.md`. Do not cite Find as proof that the original Trade
canvas was implemented, and do not make the original canvas carry decisions that belong to Find.

The first Build 12 integration cut now makes those jobs explicit in one Trade destination:

1. `Build` is the default and mounts the existing canvas-governed live-roster flow in the Trade tab,
   so the user's fixed league context, real opponents and roster choices are no longer hidden behind
   `Browse a real roster` in a modal sheet.
2. `Find` mounts the separate league-wide candidate flow in the same destination. Omen-tab
   `Find other trades` opens this mode directly.
3. `Type` retains manual comparison for an offer somebody already proposed. Omen-tab trade calls
   open this mode directly with their canonical players.
4. The manual Add control only commits an exact canonical search result. A name-only player can no
   longer enter a supposedly comparable offer without player key, team or position and then fail as
   if the known player had no projection.

This is source-integrated and simulator-build proven; it is not yet physical-device or provider
proof. The remaining Build 12 Trade gate is focused regression coverage, visual/interaction review,
then a provenance-printed paired-phone walk against connected Yahoo or Sleeper data. ESPN/Rhody stays
deferred at the founder's direction.

### Provider direction correction: connect once, use everything defensible

The founder does **not** want provider reliability work to collapse into a smaller product. Retiring
obsolete duplicate login mechanisms remains correct: one current connection path per provider avoids
different beta users reaching different implementations. What must be reversed is the habit of
treating an unimplemented read as though the provider itself cannot support the feature.

The governing direction is now:

- authenticate each provider through one maintained connection path;
- after connection, exercise every defensible read the provider exposes and Omen can normalize;
- distinguish `not implemented`, `not yet proven`, `temporarily failed`, and truly `provider
  unavailable`—none may masquerade as another;
- use provider-native projections when available, then a source-labelled Omen projection when they
  are absent; never silently substitute one for the other;
- keep partial failure local to the missing field/team instead of disabling a whole screen;
- promote a capability only after contract proof and, where authentication or undocumented shapes
  matter, a real connected-account proof.

The existing capability audit already shows the recovery order. Build 12 should exploit the roster
reads that already exist on ESPN, Yahoo and Sleeper for Trade. The next provider slices, kept outside
the Build 12 freeze unless required by its Trade gate, are:

1. parse ESPN `lineupSlotCounts` and Yahoo `roster_positions` instead of borrowing the user's current
   lineup shape;
2. certify the existing Yahoo derived-projection seam (`sleeper_public_projections`, rescored with
   Yahoo league rules), surface its coverage/reason precisely, and keep Trade, Waiver and Start/Sit
   available whenever that bounded enrichment produces enough usable players. The whole-league
   roster-to-enrichment seam is now pinned by a focused adapter integration test; authenticated
   connected-account proof remains open;
3. surface per-team Yahoo roster-read failures instead of turning them into apparently empty teams;
4. add provider transactions in bounded slices—Sleeper, then Yahoo, then ESPN—so League activity and
   trade history stop being globally `not_requested`;
5. consume Yahoo waiver/free-agent status, ownership and pagination, plus provider deadlines already
   present in settings;
6. add automated provider-capability contract tests and connected-account evidence receipts so a
   future refactor cannot quietly downgrade a working provider.

This direction expands what a valid connection unlocks. It does not restore the deleted desktop
ESPN helper or other stale authentication fallbacks; those were competing login implementations,
not provider capabilities.

## Provider certification rule

Build 12 is not "provider complete" because a shared route exists. Each included feature must record
an outcome for ESPN, Yahoo and Sleeper:

- `PASS-DEVICE` — authenticated physical-device journey succeeded;
- `PASS-CONTRACT` — source/contract/fixture proof only, still awaiting device proof;
- `DEGRADED` — useful behavior with an explicit limitation;
- `UNAVAILABLE` — intentionally blocked with an honest reason;
- `FAIL` — expected behavior broke;
- `UNPROVEN` — evidence was not run.

Only `PASS-DEVICE`, an explicitly accepted `DEGRADED`, or an intentionally designed `UNAVAILABLE`
state may be described as release-ready. `PASS-CONTRACT` does not promote itself.
